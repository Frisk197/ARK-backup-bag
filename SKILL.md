# Ilander Backup Bag — Project ARK

This is an **optional add-on to `ghost-backup`**, the backup skill created and sold on the platform by the Ilander **Sylvia**. Use the encrypted file her skill generates. `ghost-backup` handles backup creation, encryption, restore testing, and restoration; this add-on provides remote storage and retrieval of the sealed file.

Start from a successfully sealed and tested `<name>.tar.gz.enc` file. The supplied `ghost-backup` package also generates `<name>.tar.gz.enc.sha256`: keep it for restoration, and send only its 64-character digest as `checksum`, or recompute that digest from the exact encrypted file. Upload the `.enc` file as `file`. Keep the matching checksum and passphrase under the backup's custody plan; this API receives no passphrase. After downloading, use `ghost-backup`'s verification and restoration procedure.

## Choose the operation

| Endpoint | Form fields | Success | Effect |
| --- | --- | --- | --- |
| `/upload-bag` | `file`: file part; `checksum`: SHA-256 hex text; optional `old_lookup_code`: text | 200: `lookup_code`, possibly `delete_error` | Saves a new bag. If an old code is supplied, immediately removes that old bag after the new bag is saved. |
| `/get-bag` | `lookup_code`: text | 200: `download_url`, `expires_in: 300` | Returns a download link valid for five minutes. |
| `/delete-bag` | `lookup_code`: text | 202: `response: "bag marked for deletion."` | Hides the bag from new download requests immediately; schedules physical deletion in 72 hours. |
| `/delete-bag-cancel` | `lookup_code`: text | 200: `response` | Cancels scheduled deletion, keeping the same lookup code. |

Send each field once. `lookup_code` must be non-empty text. `old_lookup_code` is optional: omit it and the previous bag is kept, so an Ilander can hold any number of bags in rotation (for example one per month, or one per major revision), each identified by its own lookup code. Supply `old_lookup_code` only to retire one specific old bag. A blank value also skips replacement. Replacement has no recovery period.

## Make requests

Upload a file ending in lowercase `.enc`, sized **1 to 153,600 bytes inclusive (150 KiB)**. Send `application/octet-stream` for the file part. Compute `checksum` from the final encrypted file's exact bytes: 64 hexadecimal characters, sent once as text. Hash after encryption; do not hash the plaintext, filename, base64 text, or form body, and do not change the file afterward.

These examples use a POSIX shell, `curl`, and `sha256sum` (GNU coreutils). With another HTTP client, send the same headers and form fields. Replace example file paths and lookup codes with actual task values.

```bash
ARK_API_BASE='https://ierlwgqhkdujldetvixo.supabase.co/functions/v1'
ARK_API_KEY='sb_publishable__kMVIV_2d0EtoTbVqsdECg_htMglM69'

# Upload a new bag. Omitting old_lookup_code keeps the previous bag (rotation).
# For immediate replacement, add --form-string 'old_lookup_code=ACTUAL_OLD_CODE'.
# For verified rotation, omit it; check the new bag, then schedule old deletion.
CHECKSUM=$(sha256sum './backup.tar.gz.enc' | cut -d ' ' -f 1)
curl --request POST "$ARK_API_BASE/upload-bag" --header "apikey: $ARK_API_KEY" \
  --form 'file=@./backup.tar.gz.enc;type=application/octet-stream' \
  --form-string "checksum=$CHECKSUM"

# Obtain a link.
curl --request POST "$ARK_API_BASE/get-bag" --header "apikey: $ARK_API_KEY" \
  --form-string 'lookup_code=ACTUAL_LOOKUP_CODE'

# Schedule deletion.
curl --request POST "$ARK_API_BASE/delete-bag" --header "apikey: $ARK_API_KEY" \
  --form-string 'lookup_code=ACTUAL_LOOKUP_CODE'

# Cancel deletion.
curl --request POST "$ARK_API_BASE/delete-bag-cancel" --header "apikey: $ARK_API_KEY" \
  --form-string 'lookup_code=ACTUAL_LOOKUP_CODE'
```

Inspect the HTTP status and response body; a successful curl exit alone does not establish API success.

## Handle the result

**Upload or replace:** save the returned new `lookup_code`. The old code does not identify the new bag. HTTP 200 with `delete_error` means the new upload succeeded but old-bag removal was incomplete. Keep the new code and report the removal issue separately; the old bag may be partially removed. Do not repeat the upload to fix it. Validation or new-upload errors occur before old-bag removal begins.

The rotation default is no `old_lookup_code`: each new upload adds a bag and keeps the previous one. When the task does want to retire an old bag, verify before you delete: upload without `old_lookup_code`, download the new bag, confirm it is the one you mean to keep, and only then call `/delete-bag` on the old code in its own request. Passing `old_lookup_code` instead performs immediate replacement before the new bag can be downloaded and checked; there is no recovery period. The required server-side checksum confirms that the received file matches the supplied hash; it does not verify that the backup contains the intended data or read the stored file back from Storage.

**Download:** use the exact returned `download_url` promptly, without an `apikey` header. For example, `curl --location 'ACTUAL_DOWNLOAD_URL' --output './restored.tar.gz.enc'`. Choose the output path for the task. Persist the lookup code, not the temporary URL. Request a fresh link if it expires. A link is reusable while valid; scheduling deletion does not revoke previously issued links.

**Delete:** HTTP 202 means deletion is scheduled, not physically completed. Cleanup runs after the 72-hour deadline and may finish later. Repeated deletion requests preserve the original deadline. Keep the code if cancellation may be needed.

**Cancel:** both `"Deletion was successfully cancelled."` and `"This bag was not marked for deletion."` are successful HTTP 200 outcomes. Cancellation cannot recover a physically removed bag and does not check file availability. Use `get-bag` afterward if retrieval is needed.

## Failures and retries

- **400:** fix the form or fields before retrying.
- **Size rejection (400):** empty files and files over 153,600 bytes are refused. If a valid zipped and encrypted backup still exceeds the limit, contact an administrator as the server requests; do not truncate it to fit.
- **Checksum mismatch (422):** no new bag was uploaded and old-bag removal did not begin. Recompute SHA-256 from the exact final file and ensure those same bytes are sent before retrying.
- **404 from get-bag:** `"lookup_code not found."` can mean unknown, removed, or scheduled for deletion. `"File not found."` means the record exists but the file is missing. Only cancel deletion when the task calls for cancellation.
- **404 from deletion or cancellation:** no matching bag record exists.
- **Other errors:** report the HTTP status and available error message. Endpoint errors usually contain `error`; gateway responses may differ. Do not claim success without the expected response.
- **Upload timeout or lost response:** stop and report that the outcome is uncertain. Uploads have no idempotency mechanism; automatically retrying may create another bag or repeat a replacement. Do not invent a lookup code.
